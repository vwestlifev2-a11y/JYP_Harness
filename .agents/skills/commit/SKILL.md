# Commit

## 목적과 원칙

변경 내용을 근거로 커밋 범위와 메시지를 정한다. 실제 커밋 전에 구체적인 계획을 보여주고 사용자 승인을 받는다. 최초의 "커밋해줘" 요청은 분석을 시작하는 트리거이며, 아직 제시하지 않은 커밋 계획에 대한 승인으로 간주하지 않는다.

## 절차

### 1. 변경사항 분석

- 현재 저장소와 적용되는 프로젝트 규칙을 확인한다. Git 저장소가 아니면 알리고 중단하며, 임의로 `git init`하지 않는다.
- `git status --short`, `git diff --stat`, `git diff`, `git diff --cached`로 작업 트리와 기존 스테이징 내용을 함께 확인한다.
- untracked 파일도 포함 여부를 판단할 수 있도록 내용을 확인한다. 비밀값은 출력하거나 커밋하지 않는다.
- 변경사항이 없으면 커밋할 내용이 없다고 알리고 종료한다.

### 2. 논리적 단위로 분류

- 하나의 목적을 이루는 구현·스타일·관련 테스트는 함께 묶고, 독립적인 기능·버그 수정·정리 작업은 나눈다.
- 사용자 변경사항과 기존 스테이징 상태를 보존한다. 요청 범위가 불명확한 변경은 계획에서 별도로 표시한다.
- 관련 검증 결과와 실행하지 못한 검증을 정리한다. 검증 때문에 코드를 임의로 추가 수정하지 않는다.

### 3. 한국어 커밋 메시지 제안

메시지는 `<type>: <한국어 요약>` 형식으로 작성한다.

| type | 기준 |
| --- | --- |
| feat | 새로운 기능 또는 사용자에게 보이는 기능 개선 |
| fix | 잘못된 동작 수정 |
| refactor | 동작을 유지하는 구조 개선 |
| chore | 설정, 의존성, 문서, 기타 유지보수 |

예: `feat: 컴포넌트 작업실에 레트로 테마 적용`

각 커밋의 포함 파일 또는 변경 범위, 목적, 정확한 메시지, 검증 결과를 보여준다. 같은 파일에 독립적인 변경이 섞였다면 해당 변경 구간까지 구분한다.

### 4. 사용자 승인 후 커밋

- 위 계획을 제시한 뒤 "위 범위와 메시지로 커밋할까요?"라고 묻고 답을 기다린다. 이 승인 단계는 사용자가 요청한 본 스킬의 요구사항임을 짧게 설명하고 이 `SKILL.md`를 링크한다.
- 제시된 계획에 대한 승인이 이미 있으면 같은 승인을 반복해서 요청하지 않는다. 범위나 메시지가 달라지면 수정된 계획을 다시 승인받는다.
- 승인 후 diff를 다시 확인한다. 승인한 범위가 달라졌으면 커밋하지 말고 계획을 갱신한다.
- 승인한 파일 또는 변경 구간만 명시적으로 스테이징한다. 무조건적인 `git add .`, `git add -A`는 사용하지 않는다.
- `git diff --cached`로 실제 커밋에 승인 범위만 들어 있는지 확인한다. 기존 스테이징이 다른 범위를 포함하면 이를 임의로 해제하거나 함께 커밋하지 말고 분리 방법을 정한 뒤 진행한다.
- 메시지를 안전한 UTF-8 임시 파일로 작성하고 `git commit --file <파일>`로 커밋한다. 승인한 논리적 단위별로 반복한다.
- 훅이 실패하면 원인을 보고한다. 훅 우회, 임의 amend, reset, push를 하지 않는다. 수정으로 승인한 diff가 달라지면 다시 승인받는다.
- 완료 후 `git log -1 --oneline`과 `git status --short` 등으로 결과를 확인하고 커밋 해시·메시지·남은 변경사항을 보고한다. push는 별도 요청이 있을 때만 수행한다.
